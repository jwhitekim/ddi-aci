# Design

## Context

- 평가 규칙은 `eval_spec.md`(간단 버전, 사용자 확정)에 있다. 동기는 proposal.md의 Why 참고.
- 실행 환경: `ddi-runtime`(B), `ddi-specialist`(C), 실행기 `agent/run_agent.py`(OpenHands 0.62.0, Sonnet 5.5, 30턴, 게이트웨이 캐싱). 실행 결과는 `runs/<실행>/results/*.csv`, `trajectory.json`, `run_info.json`.
- 데이터는 쌍의 99.9%를 한 순서로만 저장하고, 모델은 순서가 있는 입력을 받는다. 순서를 바꾸면 결과가 달라질 수 있다.
- 스모크 테스트에서 B는 약물을 이름으로 적고 두 순서를 다 적었으며, 방향 뒤집힘·1칸 밀림·모델 선택 오류를 냈다. C는 ID로 한 순서만 적었다.

## Goals / Non-Goals

**Goals:**
- 질문·정답·채점이 스크립트로 재현되고, 사람은 결과 확인만 한다
- 순서 선택이나 약물 표기가 아니라 문장의 의미로 채점한다
- 10문항으로 A·B·C를 실행하고 결과를 기록한다

**Non-Goals:**
- 다른 질문 유형(순서 지정, 이름 변형, 다중 조합, 관계 필터, 신약, 미지원 약물)과 문항 확대
- C 도구 변경
- 교차 검증 모델(GPT) 실행

## Decisions

- **정답은 예측 서버와 독립된 스크립트로 계산한다 (`eval/make_ground_truth.py`).** 서버를 그대로 쓰면 C가 저절로 맞게 된다. 원 DSN-DDI 코드로 쌍 하나씩 `rels=[[0..85]]`로 계산하고, 서버와 값이 같은지(1e-4) 확인한다.
- **질문 생성과 정답 생성을 한 스크립트로 묶지 않는다.** 질문 생성(`eval/make_questions.py`)은 CSV만 읽어 호스트 파이썬으로 돌고, 정답 생성은 GPU가 필요해 `ddi-runtime` 컨테이너에서 돈다.
- **10쌍은 서로 다른 관계 10개로 고른다.** 관계별로 하나씩 무작위로 뽑아 특정 관계에 몰리지 않게 한다.
- **문장을 86개 설명 틀에 맞춰 (효과 종류, 누가, 누구에게)로 해석해 채점한다.** 설명 틀의 `#Drug1`·`#Drug2` 자리를 정규식 그룹으로 바꿔 문장과 맞추고, 잡힌 이름을 사전으로 ID로 바꾼다. 틀에 맞지 않는 문장은 "해석 불가"로 표시해 사람이 확인한다.
- **A 실행기는 OpenHands 없이 같은 게이트웨이 설정으로 질문만 보낸다 (`eval/run_baseline_a.py`).** 공통 안내 문장(저장 위치 안내)은 붙이지 않는다. A의 답에서 효과·방향을 뽑는 채점기 모델 두 개는 설정값으로 두고 실행 전에 정한다.
- **B·C는 배치 스크립트로 문항마다 `run_agent.py`를 부른다 (`eval/run_batch.py`).** 타임아웃 20분.
- **실행 전에 평가 명세와 코드를 커밋한다.** 기준을 결과 보기 전에 정했다는 기록을 남긴다.

## Risks / Trade-offs

- [10문항으로는 통계적으로 강한 주장이 어려움] → 경향과 실패 사례를 보이는 것으로 목적을 한정한다. 필요하면 같은 스크립트로 문항을 늘린다
- [에이전트 문장이 설명 틀과 조금 다르게 쓰임] → 공백·대소문자·마침표를 정규화하고, 해석 불가는 사람이 확인해 규칙을 고친다
- [두 방향을 모두 요구해서 B의 비용이 늘어남] → 사용자가 확정한 규칙. 10문항이라 총비용은 약 5~6달러
